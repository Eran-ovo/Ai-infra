把 ldmatrix 和 bank conflict 真的“看见”

GEMM v7 → v8 交互演示：32 个 lane 如何协作装载，以及 +8 half padding 为什么能把 LDSM bank conflict 降为 0。

先记住一句话：ldmatrix 负责 shared memory → 寄存器；padding 负责让 8 个行读取请求落到不同 bank。它们解决的是两个不同问题。

一、一块数据到底经过哪里？

Global memoryA、B 原始矩阵
16-byte copyuint4 / cp.async
Shared memory一个 block 内复用
ldmatrix32 lanes → fragment
mma.syncTensor Core → FP32 累加

ldmatrix 不做乘法，也不从 global memory 取数。它只接管以前“每个 lane 手工读取 half2”的 shared → register 这一段。

二、互动：为什么 v7 冲突，v8 不冲突？

每行读取连续 8 个 half，共 16 bytes，即连续 4 个 bank。切换 A/B 和 v7/v8，再观察 8 行分别点亮哪些 bank。

怎么看图：绿色表示这一 bank 只被一行命中；红色表示多个行请求在同一次 warp cooperative load 中命中了同一 bank，硬件需要把请求分批服务。

三、互动：m8n8.x4 的 “x4” 是什么？

A 的逻辑 fragment 是 16×16。ldmatrix.m8n8.x4 把它看成四块 8×8。点击四个 fragment，看哪 8 个 lane 提供该子矩阵的行首地址。

最容易误解的地方：高亮 lane 只是“提供地址”的 lane。指令完成后，不是只有这 8 个 lane 拿到数据，而是所有 32 个 lane 都拿到各自的 r0..r3 片段。

每个 lane 的指令输出：

r0 / a0r1 / a1r2 / a2r3 / a3
matrix 0: rows  0..7, cols 0..7   → a0
matrix 1: rows 8..15, cols 0..7   → a1
matrix 2: rows  0..7, cols 8..15  → a2
matrix 3: rows 8..15, cols 8..15  → a3

四、B 为什么使用 .x2.trans？

.x2

一次读取两个 8×8 fp16 子矩阵，合起来覆盖 MMA 需要的 16×8 B fragment。

.trans

shared 中仍按便于搬运的行方向存储；装载时转成 mma.sync.m16n8k16.row.col 所需的列主序寄存器布局。

.aligned

所有 32 个 lane 必须共同执行，并提供符合规范的对齐地址，不能只让分支中的部分 lane 调用。

五、padding 改了矩阵吗？

没有。padding 只在 shared memory 每行末尾加不用的空格，改变下一行从哪个 bank 开始；逻辑坐标和数值都不变。

// 逻辑数据仍然只有 BK 或 BN 个 half
A v7: [16 个有效 half]                         stride = 16
A v8: [16 个有效 half][8 个不用的 padding]     stride = 24

B v7: [64 个有效 half]                         stride = 64
B v8: [64 个有效 half][8 个不用的 padding]     stride = 72

多出的 8 个 half 是 16 bytes，所以新 stride 仍满足 uint4 和 ldmatrix.aligned 的 16-byte 对齐要求。

完整因果链：padding → 行首 bank 错开 → LDSM 不再分批执行 → shared→register 延迟下降 → GEMM 加速。

七、v9 为什么还要组合 cp.async？

cp.async 与 ldmatrix 不重复：前者优化 global→shared，后者优化 shared→register。v9 试图让“搬下一块”和“算当前块”重叠，同时保留 v8 的无冲突装载。

时间 →
stage 0: [cp.async tile 0] [ldmatrix 0 + mma 0]
stage 1:                   [cp.async tile 1] [ldmatrix 1 + mma 1]
                                   ↑ 理想情况下重叠 ↑

但双缓冲会增加 shared memory 和寄存器生命周期，所以最终是否更快仍要看 NCU，不能只看代码里是否用了更多“高级指令”。

结合源码看：ldmatrix_x4、ldmatrix_x2_trans 和 AS_STRIDE / BS_STRIDE 都在同一个实现里。
