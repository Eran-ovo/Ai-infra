GEMM：从朴素循环到手写 Tensor Core

一类算子、五版迭代：v0 朴素 → v1 smem tiling → v2 ldg → v3 CUTLASS → v4 手写 mma.sync。目标 M=N=K=1024，RTX 3060 Laptop 实测。

一、算的是什么：C = A × B

矩阵乘 C[M×N] = A[M×K] · B[K×N]，其中每个元素 C[i][j] = Σₖ A[i][k]·B[k][j]。 这是所有深度学习的核心运算（全连接层、卷积的 im2col、attention 的 QKᵀ 和 PV 都是它），也是 GPU 优化的"主战场"：一个 GEMM 算得够不够快，几乎决定了模型跑得够不够快。

C[i][j] = Σ_{k=0}^{K-1} A[i][k] · B[k][j] 工作量 = 2·M·N·K 次浮点运算（M·N 个元素 × K 次乘加 × 2）

C 的每个格子 c[i][j] 都要"读一整行 A、读一整列 B"来累加。

二、核心矛盾：算力富裕，带宽不足

GEMM 是一个 compute-bound 问题——算术强度（每字节访存能换来的浮点运算）非常高。 朴素实现的真正瓶颈不是"算不过来"，而是数据喂不饱计算单元：每个 C 元素要读 2K 个数，K 越大，重复读 A、B 的次数越多，全局内存带宽成了天花板。

所以五个版本的优化主线是同一件事：把会被反复读的数据，搬到离计算单元更近、更快的地方。加载一次、复用多次。

HBM (DRAM)→ Shared Memory→ 寄存器→ 计算单元

三、逐版原理

v0 · Naive（一线程一元素） kernels/gemm_v0.cu 3.53 ms · 607 GFLOPS

做法：每个线程负责 C 的一个元素，row、col 由线程索引推出，内层循环串行累加 K 次乘积。

for (int i = 0; i < K; ++i)
    sum += A[row*K + i] * B[i*N + col];

瓶颈：每个线程读 K 次 A 和 K 次 B，这些读取大多来自全局内存，且同一行 A / 同一列 B 被不同线程重复读。全局内存往返次数 = 2·K 次/元素，带宽被完全打爆。v0 的唯一价值是正确性基线。

v1 · Shared Memory Tiling（分块复用） kernels/gemm_v1.cu 2.77 ms · 779 GFLOPS（~1.3x）

核心思想：把整个乘分成 TILE×TILE 的小块，每块的 A、B 子块先由 block 全体线程搬进 shared memory，然后 block 内所有线程从 smem 反复读。这样全局内存里每一块数据只被搬一次，剩下的复用全部走 smem。

#define TILE 32
__shared__ float As[TILE][TILE];
__shared__ float Bs[TILE][TILE];
for (int t = 0; t < K/TILE; ++t) {
    As[ty][tx] = A[row*K + t*TILE+tx];   // 协作搬入
    Bs[ty][tx] = B[(t*TILE+ty)*N + col];
    __syncthreads();                      // 搬完才能算
    for (int k = 0; k < TILE; ++k)
        sum += As[ty][k] * Bs[k][tx];     // 从 smem 读，复用
    __syncthreads();                      // 下一轮要覆盖，先等算完
}
global → smem As/Bs → 32 线程从这重复读

下面这块 6×6 就是搬进 smem 的一个 tile：搬一次，块内 16×16 个线程反复读它算各自的 C——这是"加载一次、复用多次"的全部含义。

为什么无 bank conflict：

  • As[ty][k]：同一 warp 内 ty 相同、k 相同 → 32 线程读同一地址 → 广播，无冲突；
  • Bs[k][tx]：tx 0~31 连续 → 32 线程读 32 个连续地址 → 落在 32 个不同 bank，无冲突。

注释里的反例（Bs[tx][k] 列优先访问）会造成 32 路冲突，修法是 Bs[TILE][TILE+1] pad 一列。

v2 · Coalesced + __ldg 只读缓存 kernels/gemm_v2.cu 2.72 ms · 789 GFLOPS（+1.3%）

核心思想：v1 已经把搬运做成了合并访存（地址连续 4B 递增 = 1 个 128B 事务）。v2 在 v1 基础上把 A/B 的全局加载改成 __ldg，走只读数据缓存（read-only cache / texture pipeline），并加上 __restrict__ 承诺指针不别名，让编译器更敢优化。

As[ty][tx] = __ldg(&A[row*K + t*TILE+tx]);   // 走只读缓存

收益与意义：只比 v1 快 1.3%——说明"合并访存"这一最大头成本 v1 已拿到，v2 只是在带宽尾数上再抠一点。它验证了一个判断：访存微调的空间已近天花板，要靠换算法（Tensor Core）才有量级飞跃，这正是 v4 的动机。

v3 · CUTLASS（工业级实现） kernels/gemm_v3_cutlass.cu 0.408 ms · 5259 GFLOPS（~6.5x）

核心思想：直接调 NVIDIA CUTLASS 的 cutlass::gemm::device::Gemm，把 tile/warp/流水线配置在编译期固化，几乎零运行时开销。

using Gemm = cutlass::gemm::device::Gemm<float, RowMajor, float, RowMajor, float, RowMajor>;
Gemm::Arguments args({M,N,K}, {dA,K}, {dB,K}, {dC,N}, {dC,N}, {alpha,beta});
gemm_op(args);

意义：v3 不是"手写版"，而是性能天花板参照物——它告诉你在同一块 GPU 上，GEMM 能做到多快（5259 GFLOPS）。与手写 v1 的 6.5 倍差距，就是 CUTLASS 的 Tensor Core + 软件流水线 + 深层次 warp 分块 贡献的价值，也是 v4 要逼近的目标。

v4 · 手写 Tensor Core（fp16 mma.sync） kernels/gemm_v4_mma.cu 0.542 ms · 3963 GFLOPS（1024³ 单次）

核心思想：绕开 wmma API 和 CUTLASS，直接内联 PTX 指令 mma.sync.aligned.m16n8k16.row.col。把 v2 的"每周期 32 个 lane 各做 1 次乘加"（FMA）换成"每条指令整个 warp 完成 16×8×16=2048 次乘加"。

global fp16 A/B→ smem tile→ fragment(寄存器)→ mma.sync→ fp32 acc→ global C

下面这条 seeker 红框沿 K 维扫过：它就是 mma 每次"一口气吃掉 16 个 K 值、把 2048 次乘加攒进输出块"的动作。每个 c 格子在红框扫过的全程里持续累加。

A16×16k=0k=1k=2
B16×8k=0k=1k=2
C16×8cc…

红框每滑一格 = 一次 mma.sync。A 取 16×16 的一块、B 取 16×8 的一块，输出累加到 C 的 16×8。

A 用 fp16，累加器 C 用 fp32——这就是"输入半精度、累加全精度"，精度不掉、速度翻好几倍的关键。

为什么必须先过 smem

mma 指令要求输入按 fragment 布局 存放——每个 lane 持有的不是连续内存，而是"乱序"的特定位置（如 (g, 2·gid)）。若直接从 global 按这个布局读，会打散合并访存（coalesced）。正确姿势是：先用全体线程按 tid, tid+256, … 连续顺序合并地搬进 smem，再从 smem 按 fragment 布局自由索引（smem 带宽高、代价小）。这就是"分块搬 + 按需取"两步走。

fragment 布局（踩坑重灾区）

设 g = lane/4（groupID，0~7）、gid = lane%4（组内 id，0~3）：

矩阵每 lane 持有精确布局
A (16×16 row-major)4×half2 a0..a3a0=(g,2gid) a1=(g+8,2gid) a2=(g,2gid+8) a3=(g+8,2gid+8)
B (16×8 col-major)2×half2 b0,b1b0=(2gid,g)/(2gid+1,g) b1=(2gid+8,g)/(2gid+9,g)
C (16×8 fp32)4×float c0..c3c0=(g,2gid) c1=(g,2gid+1) c2=(g+8,2gid) c3=(g+8,2gid+1)
踩坑判据：A fragment 的 a1/a2 行索引写反 → 输出"前 16 行对、后 48 行错"的不均匀错位（而非全错）。这类"一半对一半错"是 fragment 映射 bug 的标志。定位手法：单 block + A=单位阵 + B=行号的确定性用例，dump 一列即可看出哪半块错位。

正确性对拍的两个坑

  • CPU 必须吃同一份 fp16 量化后的输入：0.2、0.4 这类值 fp16 无法精确表示，若 CPU 参考用原始 float、GPU 用 fp16，两边基准不同会误报 FAIL。做法：先把输入转 fp16 再转回 float，CPU 用这份转回来的数据。
  • 阈值用相对误差：fp16 GEMM 的绝对误差随 K 线性增长（累加项越多误差越大），绝对阈值在大规模必然误判，要除以参考值幅度。

如何读性能数字（避免误判）

  • 2048 比 1024 慢 8 倍是健康的线性扩展（工作量 2·M·N·K ∝ D³，边长翻倍→8 倍）。判断标准看 GFLOPS 是否持平：1024→2048→4096 = 2847→3620→4322 GFLOPS，持平即健康。
  • 若超出 8 倍（GFLOPS 塌陷）→ 笔记本 GPU 撞 TDP/温度墙降频。判定铁证：同一进程里 cuBLAS 也按同比例变慢（cuBLAS 不受我们 kernel 影响）。
  • 测量口径：单次 0.754ms vs 20 次平均 0.448ms 差异大——首次启动有冷缓存/未达稳态频率的开销，两种口径都要记录，避免"到底多少 GFLOPS"的歧义。
