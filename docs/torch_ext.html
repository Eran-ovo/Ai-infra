PyTorch 封装：把手写 kernel 变成 torch 算子

把 kernels/ 下 5 类手写算子（GEMM / Softmax / LayerNorm / RMSNorm / FlashAttention）统一封装成一个 PyTorch Extension 模块 ai_infra_ops —— 工业界标准的 CUDA → PyTorch 落地流程。

先区分“5 类”和“9 个函数”：这里有 5 类能力；GEMM 提供 baseline/Tensor Core，FlashAttention 提供 v3/v4/v5/v6 四个入口，所以绑定层一共暴露 9 个 Python 函数。
这一层解决的不是算法问题，而是边界问题：Python 的 Tensor 如何验证、如何取到底层指针、如何配置 grid/block、如何把 CUDA 错误和结果安全地交还给 Python。真正的计算仍发生在 .cu kernel 中。

一、为什么需要这一层：kernel 只是"半成品"

kernels/ 里的算子都是独立的 main()：自己 malloc、自己喂数据、自己对拍。它们是学习/验证用的，无法被 Python 直接调用。 要让这些手写 kernel 真正可用（写进模型、接进训练/推理），必须把它们暴露成 torch.xxx() 形式的算子——这就是 torch_ext/ 干的事。

手写 CUDA kernel (.cu)→ torch::Tensor 包装层（校验 + launch）→ PyBind11 绑定（bindings.cpp）→ setup.py 编成 .so→ import ai_infra_ops

二、一次 Python 调用到底发生了什么

进入绑定函数：m.def(...) 把 Python 参数转换成 C++ 的 torch::Tensor、double 或 bool。
检查契约：TORCH_CHECK 验证设备、dtype、维度、形状和连续性；失败时抛出 Python 可见的异常，不让非法指针进入 kernel。
准备输出与参数：包装层根据输入 shape 创建输出 Tensor，并从 Tensor 读取 data_ptr<T>()、M/N/K 或 N 等 launch 参数。
启动 CUDA：计算 grid/block 后调用 <<<grid, block>>>；kernel 在 GPU stream 上执行，包装函数返回一个仍由 PyTorch 管理生命周期的 Tensor。

生命周期为什么安全：输出由 torch::empty/empty_like 创建，底层内存由 PyTorch allocator 管理；包装层只在 kernel 执行期间借用裸指针，不负责手动 malloc/free。

四、每个算子的三层结构（以 RMSNorm 为例）

每个算子都是一模一样的三段：kernel 不变 + 加一层 Tensor 包装。kernel 主体直接照搬 kernels/rmsnorm_v1.cu，差异只在输入输出从裸指针换成 torch::Tensor。

第 1 层：CUDA kernel（同源，几乎不改）

__global__ void rmsnorm_fused(const float* __restrict__ x,
                              const float* __restrict__ g,
                              float* __restrict__ y, int N, float eps) {
    // ... 与 kernels/rmsnorm_v1.cu 完全一致的归约 + 归一化逻辑
}

第 2 层：torch::Tensor 包装（数据校验 + 拉参 + launch）

torch::Tensor rmsnorm_forward(torch::Tensor x, torch::Tensor g, double eps) {
    TORCH_CHECK(x.is_cuda() && g.is_cuda(),        "x/g must be CUDA tensors");
    TORCH_CHECK(x.dtype() == torch::kFloat32,      "x must be float32");
    TORCH_CHECK(x.is_contiguous() && g.is_contiguous(), "x/g must be contiguous");
    TORCH_CHECK(x.dim() == 2,                      "x must be [B, N]");

    auto y = torch::empty_like(x);
    rmsnorm_fused<<<B, BLOCK>>>(x.data_ptr<float>(),
                                    g.data_ptr<float>(),
                                    y.data_ptr<float>(), N, (float)eps);
    return y;
}

第 3 层：PyBind11 绑定

PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("rmsnorm", &rmsnorm_forward, "RMSNorm forward (CUDA)");
}

五、面试关键点（这层最常被问）

1. TORCH_CHECK 防御性校验
  • 进入 kernel 前先校验 device / dtype / contiguous / 维度——kernel 本身不做任何检查，非法输入会直接越界或算错，必须在包装层挡掉。
  • 这是「C++ 与 Python 的边界安全」：Python 侧拿到的任何 tensor 都可能来自任意设备/类型。
2. contiguous 为什么必须检查

kernel 用 x + row*N 这种线性地址定位元素，前提是内存连续。非连续 tensor（如转置视图、切片）用同样的指针算术会读到错误位置。

TORCH_CHECK(x.is_contiguous(), "x must be contiguous");
// 或者工程上更友好：x = x.contiguous();  // 就地转成连续副本
3. data_ptr<T>() 拿裸指针

x.data_ptr<float>() 返回 tensor 底层内存的 float*，传给 kernel 当 const float* 用。包装层与 kernel 之间靠「指针 + 形状参数（M/N/K）」约定，这正是 CUDA C 拉内核的标准姿势。

4. 单一模块 vs 多 .so

一个 ai_infra_ops 模块暴露全部 9 个 Python 函数，而不是每个算子一个共享库。工业界（FlashAttention 官方 repo、DeepSpeed op）都这么做：

  • 一次 import 全部可用，编译一次而非 N 次；
  • 共享符号与头文件，operator 间可互相复用代码。
5. 运行时 bool → 编译期模板（FlashAttention 的 causal）

causal 是 Python 传进来的运行时 bool。若直接 if (causal) 放进 kernel 每轮循环判断，会浪费每轮一次分支。做法是在包装层 if/else 派发到两个编译期实例：

if (causal) flash_fwd<true><<<grid, Br>>>(...);
else        flash_fwd<false><<<grid, Br>>>(...);

kernel 内部 template<bool IS_CAUSAL> 把 mask 条件在编译期固化，运行时零分支开销。

6. ABI 一致 + 架构白名单
  • ABI：setup.py 编译时 torch 自动对齐 _GLIBCXX_USE_CXX11_ABI，保证 C++ 标准库与 PyTorch 一致，否则 link 时符号错乱。
  • TORCH_CUDA_ARCH_LIST：export TORCH_CUDA_ARCH_LIST="8.6" 只对目标架构（sm_86）编译，避免对所有架构浪费时间。

六、实测结果（RTX 3060 Laptop，test_all.py 复现）

下表比较的是同一输入规模下的端到端 kernel 时间；加速比按“PyTorch 原生时间 ÷ 手写时间”计算。它用于说明优化方向，不是对所有 batch、特征维度和 GPU 的普遍保证。

算子手写 CUDAPyTorch 原生加速比结论
RMSNorm (B=1024 N=1024)0.031 ms0.156 ms4.97xfused 少写回中间结果
Softmax (B=1024 N=1024)0.031 ms0.030 ms0.98xtorch 本身已融合，打平合理
LayerNorm (B=1024 N=1024)0.040 ms0.125 ms3.11x同上
GEMM (1024³)3.04 ms0.33 ms (cuBLAS)0.11x手写 tiled vs cuBLAS 真实差距
GEMM mma fp16 (1024³)0.542 ms0.237 ms (cuBLAS fp16)0.44xTensor Core 后差距从 13x 缩到 2.3x
FlashAttention (N=8192 D=64)causal 9.95 ms—causal 2.06x中间结果不落显存，结果只写回一次
FlashAttention v4→v5 (N=8192 D=64)full 4.2508→3.3810 ms—1.26x删除 Ps，occupancy 16.67%→25%
FlashAttention v6 (B=2 H=2 N=4096 D=128)full 7.3629 ms1.8643 ms (SDPA)3.95x正确但受寄存器/片上容量限制
为什么归一化类能赢、GEMM 输得惨：归一化（RMSNorm/LayerNorm）是 memory-bound 问题——手写 fused 一次加载一次写回，天然赢过 PyTorch 拆成 pow→mean→rsqrt→mul 的多次读写；而 GEMM 是 compute-bound，对手是 cuBLAS 的 Tensor Core + 深度流水线，手写 tiled 不换硬件必输。一胜一负，恰好印证「优化要先分清 bound 类型」。

七、编译与使用

编译阶段生成带有 CUDA kernel 的共享库；运行阶段只需导入它。两者是不同问题：改了 .cu 或 CUDA/PyTorch 环境要重新编译，普通 Python 调用不会再次编译。

cd torch_ext
export PATH=~/venvs/torch/bin:/usr/local/cuda/bin:$PATH
export TORCH_CUDA_ARCH_LIST="8.6"
~/venvs/torch/bin/python setup.py build_ext --inplace
~/venvs/torch/bin/python test_all.py
import ai_infra_ops
ai_infra_ops.rmsnorm(x, g, eps)          # x [B,N] fp32, g [N]
ai_infra_ops.softmax(x)                  # x [B,N] fp32
ai_infra_ops.layernorm(x, eps)           # x [B,N] fp32，无 affine
ai_infra_ops.gemm(a, b)                  # a [M,K] b [K,N] fp32 -> fp32（tiled）
ai_infra_ops.gemm_mma(a, b)              # a [M,K] b [K,N] fp16 -> fp32（手写 Tensor Core）
ai_infra_ops.flashattention(q, k, v, causal)  # q/k/v [N,64] fp32
ai_infra_ops.flashattention_fp16(q, k, v, causal)  # v4 [N,64] fp16
ai_infra_ops.flashattention_v5(q, k, v, causal)    # v5 [N,64] / [B,H,N,64] fp16
ai_infra_ops.flashattention_v6(q, k, v, causal)    # v6 [N,128] / [B,H,N,128] fp16

遇到报错时按这个顺序排查

设备：确认输入位于 CUDA，且当前 GPU 支持目标架构；CPU Tensor 会在入口的 TORCH_CHECK 处被拒绝。
类型与形状：确认 fp32/fp16 要求、二维/四维 shape、GEMM 的内维相等，以及 FlashAttention 的最后一维为 64 或 128。
连续性：对转置或切片结果调用 .contiguous()；仅仅 shape 看起来正确，并不代表底层地址是线性排列。
性能：先 warm-up，再用 CUDA event 计时；首次调用还可能包含 lazy initialization，不能拿它和稳态平均值直接比较。
