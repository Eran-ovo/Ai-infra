FlashAttention：分块 + Online Softmax

七个版本复现 FlashAttention 数据流：v1 分块 + online softmax → v2 causal → v3 warp-per-row → v4 fp16 Tensor Core → v5 P fragment 寄存器直连 → v6 D=128 → v7 Q fragment 寄存器缓存。核心主张始终是「让 S 矩阵永不落地 HBM」。

一、先看标准 attention 哪里"贵"

给定 Q/K/V ∈ RN×D，单头标准 attention 是两步矩阵乘夹一个 softmax：

S = Q · Kᵀ / √D (N×N 的分数矩阵，O(N²D) 次运算，O(N²) 内存) P = softmax(S) (按行归一化) O = P · V (N×D 输出)
每个下标代表什么：Q 的第 i 行是第 i 个 token 发出的 query，K/V 的第 j 行是第 j 个 token 的 key/value。S[i][j] 衡量 token i 是否应该关注 token j；softmax 沿 j（同一 query 对所有 key）做，因此 P[i] 是一组和为 1 的注意力权重，最后用它对 V 加权求和。
FlashAttention 的目标不是少算数学结果：它仍然计算同一个 O = softmax(QKᵀ/√D)V，只是把 N×N 的中间矩阵拆成小块，在片上完成“打分 → softmax → 加权求和”，让中间结果不必写回 HBM。

朴素实现的瓶颈：S 矩阵大小是 N×N，对长序列（N=8192）是 8192²×4B ≈ 256MB；P 通常还要再占一份同规模空间。必须把 S 写回全局内存（HBM）再读回来做 softmax 和 ×V——这一写一读完全受 HBM 带宽限制，也让显存占用按 N² 增长。

中间那个 S（划掉 = 不应该存在！）在朴素实现里要先写进 HBM 再读回来——FA 的整个设计就是让它根本不落地。

二、核心思想：分块 + Online Softmax

FlashAttention 的洞见有两点：

  1. 分块（tiling）：把 K/V 切成 Bc 行一块，每次只算 S 的一小条 Br×Bc，在片上算完 softmax 和 ≤×V 的贡献，S 块用后即弃——永远不落 HBM。
  2. Online Softmax：softmax 的 max 和 sum 可以"流式"维护，不用等所有分数算齐。每来一个新块，旧统计量用一个系数 alpha 修正即可。

Online Softmax 的数学（关键）

对每一行，维护三个运行量：m（迄今最大分数）、l（Σexp(S-m)）、acc（Σexp(S-m)·V，未归一化分子）。每处理一个新块，新旧两块合并：

m_new = max(m_old, m_row) // m_row 是本块最大分数 alpha = exp(m_old - m_new) // 旧最大变小 → 旧统计要按比例缩小 l_new = alpha·l_old + Σ_c exp(S[c]-m_new) acc = alpha·acc + Σ_c exp(S[c]-m_new)·V[c]

直觉：旧的最大值若被新块超过，旧块的 exp(S-m_old) 全部偏大，乘 alpha 统一缩回去，再叠上新块的贡献。最终 O = acc / l。这就是"不必回头、单遍扫过 KV"的全部依据。

为什么这样仍等价于普通 softmax：处理到任意一个 KV 块后，都保持不变量 l = Σ exp(S-m)、acc = Σ exp(S-m)V，其中求和只覆盖已经扫描的列。若新块抬高了 m，旧项统一乘 exp(m_old-m_new)，不变量仍成立；扫完最后一块时，acc/l 正好就是完整 softmax 的加权平均。
Q 行(驻寄存器)→ 逐块搬 K/V 进 smem→ 算 S 块 + online softmax→ 累加 O(=acc/l)→ 写回

把一个 Q block 的执行顺序展开

保留 Q：将一小块 Q 行放入寄存器或 shared memory；这些行会反复与不同的 K/V 块计算。
加载 K/V：协作把当前 Bc 行 K、V 搬进 shared memory，所有线程等待搬运完成。
计算分数块：对当前 Br×Bc 的分数做缩放；causal 模式下，未来位置设为负无穷，相应概率为 0。
在线更新：用新块的 max、alpha、sum 更新 m/l/acc，随后立即丢弃当前 S 块。
最终写回：所有 KV 块扫完后才做 O = acc/l，每个输出元素只写回一次。

空间复杂度的直觉：朴素 attention 需要保存整个 N×N 的 S/P；分块实现只保留 Br×Bc 的分数块、Bc×D 的 K/V tile 和 Br×D 的累加状态，临时空间随 tile 大小增长，而不是随序列长度平方增长。

分块扫描长什么样——下面这个 seeker 就是逐块搬进来的 K/V 块，它从左往右扫过一整行 Q；每扫一块，就更新一次 O（那个小方块）：

Q行 K₀K₁K₂K₃K₄
S条s₀s₁s₂s₃s₄
O +++++

绿框每扫一格：算这条 S 的分数 → 在线 softmax → 累进 O。全程 S 只是一条短向量，从不出片上。

Online Softmax 的状态怎么"边扫边改"

盯住"迄今最大分数 m"和"累积和 l"这两个数，扫到第 2 块时若发现新块有更大的分数，旧统计就要打个折（alpha）再叠新的：

扫到块 0m = 3
扫到块 1m = 5 ← 更大
alpha = exp(3−5)e⁻² ≈ 0.135
l 修正l = 0.135·l_old + Σexp(s−5)
最终O = acc / l

max 被顶高时，之前所有 exp 都要乘 e^(m_old−m_new) 缩回去——这就是 alpha 的作用，让统计量"永远跟得上最新的 max"。

三、逐版原理

v1 · 分块 + Online Softmax kernels/flashattention_v1.cu 0.199 ms · N=512, D=64, Br/Bc=32

线程映射：一线程一行。每 block 处理 Br=32 行 Q、block 内 32 线程各管一行，逐块搬 Bc=32 行 K/V 进 smem，内层循环扫完所有 KV 块。

关键结构：Q 行全程驻在寄存器 q_reg[D]（外层循环复用，不回 HBM）；每轮把 S[Bc] 这一小条分数在寄存器里算完、做完 online softmax、累进 acc[D]——S 从不写回全局内存。

这版的价值：验证了 online softmax 的数值正确性（maxErr 2.4e-07 与标准实现一致），并建立了分块骨架。问题也同时埋下：一线程一行导致每个 block 只有 1 个 warp，occupancy 极低（见 v3）。

v2 · Causal Mask（模板双模式） kernels/flashattention_v2.cu full 9.43 / causal 4.71 ms · N=8192 · causal 2.00x

加了什么：GPT 自回归的 causal mask——第 q 行只能看到 j≤q 的 KV（下三角）。用 template<bool IS_CAUSAL> 做编译期双模式，运行时 bool 在包装层 if/else 派发，kernel 内无运行时分支。

// 块级截断：整块跳过未来信息
const int kv_end = IS_CAUSAL ? (q_row_max / Bc + 1) : num_kv_blks;
for (int kv_blk = 0; kv_blk < kv_end; ++kv_blk) {
    ...
    if (IS_CAUSAL && kv_col > q_row) { S[c] = -1e20f; continue; }  // 对角线块逐元素 mask

两层式因果：① 循环上界按 block 粒度截断（必须全 block 一致，否则 __syncthreads 被最慢线程拖着走，省不了块）；② 对角线块内再逐元素 mask。causal 理论上省一半计算（只算下三角），N=8192 时实测 2.00x ——恰好命中理论上限。

踩坑：初版在 N=512 时 causal 反而 0.84x（负优化）。ncu 定位：occupancy 仅 2.08%，每 block 只 1 个 warp，内存延迟完全无法隐藏，省下的计算被串行延迟淹没。教训：低 occupancy 下谈计算量优化是空中楼阁。

causal mask 就是只留左下三角——右上角全是不该看的"未来"，直接跳过：

✓✗✗✗✗
✓✓✗✗✗
✓✓✓✗✗
✓✓✓✓✗
✓✓✓✓✓

✓ = 算（下三角），✗ = 跳过（上三角）。正好省一半 → 实测 causal 2.00x 就是命中这个理论值。

v3 · Warp-per-row（FA2 的核心重划分） kernels/flashattention_v3.cu full 17.7 / causal 8.8 ms · N=8192 · causal 2.01x

解决什么：v2 一线程一行的架构，每线程要同时持有 q_reg[64] + acc[64]，寄存器爆炸 → 每 block 只能 1 warp → occupancy 2%。

改法（对齐 FA2 思想）：一 warp 一行。block = 256 线程 = 8 warps，每 warp 独占一行 Q，warp 内 32 个 lane 分摊 D=64 维（每 lane 只存 q_reg[2] + acc[2]）。寄存器需求从 ~130 降到 ~40/线程，occupancy 2% → 79%。

// 每个 lane 只负责 DQ=D/32=2 维
__shared__ float Ktile[Bc][D+1];   // 【padding】行宽 65 与 32 互质
__shared__ float Vtile[Bc][D+1];
// 每 lane 独立算自己那行 K 的完整点积（Bc==WARP，c=lane 正好一个分数）

三个踩坑（教训）：

  • 发散分支禁用跨 lane shuffle：初版在 causal 分支下用 __shfl_xor 归约 → 直接死锁。解法：每 lane 独立算完整点积，不再跨 lane 凑。
  • 不能 return 提前退出：if(q_row>=N) return 会让部分 warp 退出、留下 __syncthreads 死等。改 valid 标记"陪跑"。
  • 列访问 bank conflict：K/V 按列访问时地址步长 = D。D=64 是 32 的倍数 → 全撞同一 bank（9.4 亿次冲突）。修法 Ktile[Bc][D+1]，步长 65 与 32 互质，冲突降 14x。

仍比 v2 慢 1.8x 的归因：K/V 随 block 数增多重复搬运 + Q 点积冗余。说明 occupancy 与算术强度是三角债，拉满一个可能拖累另一个。

v4 · fp16 + 手写 Tensor Core（复现 FA2 的关键一步） kernels/flashattention_v4.cu N=8192 full 4.2508 ms

解决什么：v3 是 fp32，QKᵀ 和 PV 两个矩阵乘仍是 FMA 逐点算。与 GEMM v4 同理——真正复现 FA2 性能要把这两个 GEMM 换成 Tensor Core。

改法：Q/K/V 用 fp16，累加和 softmax 用 fp32。S = Q@Kᵀ 和 O += P@V 都用 mma.sync.m16n8k16。

  • warp 划分对齐 FA2：每 block 处理 Bq=64 行 Q，4 个 warp，每 warp 独占 16 行（正好一个 mma 的 M-tile）。
  • 行归约全在 warp 内：每 warp 扫全部 K/V 块，softmax 的 max/sum 归约不跨 warp 通信，直接继承 v3 的在线软 max。
  • fragment 布局复用 gemm_v4 的已验证版：load_A_verified 直接搬 gemm_v4 的 A fragment 布局（a0~a3），踩过的坑不再重踩。
  • 清晰的 P 数据通路：softmax 后先把 P 写入 padded Ps[64][65]，PV 前再按 A fragment 布局加载；多一次 smem 中转，但便于验证正确性。

当前边界：Bq=Bc=D=64 固定；full/causal 两种模式都通过模板特化，K/V 尾块与 causal 未来位置均使用 score mask，N 可以不是 64 的倍数。

v5 · P fragment 寄存器直连 kernels/flashattention_v5.cu N=8192 full 3.3810 ms · v4/v5=1.26x

观察：QK 的每个 m16n8 输出 fragment 已经按行分散在 S[t][0..3] 中；相邻两个 8 列 fragment 正好能拼成 PV 所需的 row-major m16k16 A fragment。无需把 P 写入 Ps 再读回来。

pa0 = half2(S[st][0],     S[st][1]);      // row g,   cols 0..7
pa1 = half2(S[st][2],     S[st][3]);      // row g+8, cols 0..7
pa2 = half2(S[st + 1][0], S[st + 1][1]);  // row g,   cols 8..15
pa3 = half2(S[st + 1][2], S[st + 1][3]);  // row g+8, cols 8..15

证据链：v4/v5 在 N=129 full/causal 的误差逐项相同；static smem 33.28→24.96 KB（恰好减少 64×65×2=8,320 B）；理论 occupancy 16.67%→25%，实测 15.55%→21.28%；N=8192 full/causal 提速 1.26x/1.17x。

批量多头：同一 kernel 进一步用 grid.x 枚举 Q block、grid.y 枚举展平的 batch×head，同时支持 [N,64] 与连续 [B,H,N,64]。B=2/H=8/N=1024 时，相比 Python 逐 head dispatch，full/causal 分别减少到 1/3.11 和 1/5.13 的耗时。

关键认识：fragment 不是只能“从 shared memory 加载”的黑盒。只要证明生产者的 C-fragment 布局与消费者的 A-fragment 布局之间的映射，就可以直接在寄存器中重排，消除中间存储。
v6 · D=128 扩展实验 kernels/flashattention_v6.cu B=2,H=2,N=4096 full 7.3629 ms

不是改一个宏：D=128 让 QK 的 reduction step 从 4 变成 8，Q/K/V shared-memory 行宽从 65 变成 129，PV 输出 tile 从 8 变成 16。v6 保留 v5 的 register-P 映射，因此 P 仍然不经过 shared memory。

资源代价：static shared memory 49.54 KB，full/causal 分别使用 128/163 registers per thread，理论 occupancy 为 16.67%，但无 spill。causal 路径的高寄存器压力说明下一步应研究 accumulator 生命周期、Bq 重新分块或 tile 设计。

学习重点：head dimension 是 kernel 设计参数，不是普通 shape 参数。它同时改变算术工作量、shared-memory 容量、寄存器文件占用和 occupancy，必须用 ptxas + NCU + benchmark 一起判断。
v7 · Q fragment 寄存器缓存 kernels/flashattention_v7.cu D64 N=1024 full · 相对 v5 1.13x

假设：v5 每扫一个 KV tile 都会重新从 shared memory 加载同一份 Q fragment；长序列中这份重复片上搬运会放大 MIO 压力。

改法：Q 先合作式进入 shared memory，再把每个 lane 需要的 MMA fragment 缓存在寄存器中并跨 KV tile 复用；Q/K 同时复用一块 shared tile，使 static shared memory 从 24.96 KB 降到 16.64 KB。

验证：full 路径实测 occupancy 从 22.92% 提升到 28.64%；正式报告中 [2,8,1024,64] 和 [2,8,2048,64] full 相对 v5 分别加速 1.13x/1.12x。短序列收益不稳定，因此稳定入口只在 D=64 && N>=1024 时路由 v7。

关键认识：降低 shared memory 不一定降低片上压力——寄存器会增加，MIO stall 占比也可能上升。最终调度阈值必须来自 shape 扫描，而不是只看单个 NCU 指标。

四、七版区别总览

版本线程映射精度causal核心增量
v1一线程一行fp32否分块 + online softmax（S 不落 HBM）
v2一线程一行fp32✔ 模板双模式causal 块级截断 + 逐元素 mask
v3一 warp 一行fp32✔warp-per-row 寄存器瘦身 + padding 消 bank conflict
